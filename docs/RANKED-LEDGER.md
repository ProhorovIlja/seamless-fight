# Durable ranked-set result ledger (offline candidate)

`server/ranked-ledger.mjs` uses Node's built-in `node:sqlite` for atomic updates of both Glicko-2 participants and an immutable set result. Its tests use a temporary on-disk SQLite database, restart the database connection, verify exactly-once idempotency, reject conflicting duplicate result claims and verify two-player updates roll back if validation fails. It uses prepared SQL statements, transactions, WAL mode for on-disk writes and `synchronous=FULL`. Provisional players are excluded from standings unless a minimum qualifying-set count is specified.

**It is NOT imported by server.mjs, exposed over HTTP, granted to casual/preview clients or deployed.** The caller must be an authenticated, trusted server authority supplying both player identities and the outcome of an authoritative complete first-to-two set. No player API accepts, computes or submits ranked points yet. The SQLite file must live on a dedicated writable data volume (with encrypted backups and off-host restore tests), not the root-owned read-only source tree used by the current Debian 13 dynamic systemd user. An eventual production service needs explicit account authentication, authenticated session-to-room bindings, unique durable match-set nonces, reconnect/disconnect policy, privacy/delete controls, abuse/audit controls, rate limiting and transactional finalization. Only then can this candidate be integrated.

No SQL queries accept browser-provided column names or executable schema fragments. The ledger keeps ratings and sets separately per season. Replaying an identical committed set never changes ratings, while a conflicting result for the same immutable set ID fails closed. A global unique index on the server-authored set ID additionally prevents re-crediting the same physical match in a later season. If an older offline test database already contains the same set ID in multiple seasons, opening it fails closed when this unique index is created; inspect and reconcile those conflicts before any migration. This offline guard is not an account authenticator and does not make the ledger safe to expose to browsers.

Node 22's built-in `node:sqlite` remains experimental. Test and pin the runtime and the SQLite serialization ABI before enabling any live ranked economy; Node 24 or a stable external SQLite package may be preferable at deployment. The current supported Debian 13 CI runs Node 22 and 24.
